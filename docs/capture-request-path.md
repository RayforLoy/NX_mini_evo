# C05 之后的实际拍摄请求路径

本记录针对官方 NX mini 1.10，整包 SHA-256 为 `8a5bbe8885df239739f85f92087fea3972c05f98bd6521d809ed60dd5aca89fa`。依据是段 1 原始指令、实际派生类虚表和局部反编译；下文不是整机执行或拍摄测试结果。对应机器可读核对记录为 `research/generated/native-capture-request-static.json`。

## 从拍摄分发到请求出口

C05 r2 的 S2 探针终点仍是模式虚表 `+0xf0`；本次没有扩大该探针的执行范围。静态追踪继续经过公共 `doPhotoCapture`（`0x4014f51c`），最后通过相机对象的 `+0xf8` 调用拍摄 API。

启动构造函数绑定的 `CCamSystemImpl` 主虚表是 `0x4076f5f0`，其 `+0xf8` 指向 `0x406c1c94`。该函数日志为 `CALL camPhotoCapture`。它按相机对象 `+0x225` 中的内部拍摄类型选择路径；普通分支会调用 `0x406c1c4c`，参数包含请求值 `0x100000`。这个内部类型不能直接等同于 UI 模式编号。

`0x406c1c4c` 会在类型变化时等待并执行配置函数 `0x4001ec0a / 0x4001ec52`，随后调用 Thumb 函数 `0x403e0926`，并增加 `0x41896f30+0x3c` 计数。`0x403e0926` 经 `0x403e08f8` 写入请求状态，再调用内核相关函数。没有执行这些等待、驱动配置、内核调度、图像处理或文件写入，不能把到达请求出口称为已经拍摄。

## 不能把返回成功当作生成照片

`0x406c1ccc–0x406c1d0c` 检查共享状态 `CORE+8` 的 `0x10000000` 标志。标志为真时，该函数走消息／回调路径，跳过正常拍摄请求，最后仍返回 1。此前定位的 `I:/nolens.txt` 生产入口会设置这个标志。因此，该入口及 API 成功返回值不能作为普通免短接拍摄修复的依据。这是静态调用与分支关系推断，尚未在机身上执行该入口。

另一项退出条件是 `0x403e0b64` 返回值的 `0x100000` 位：非零时，函数打印上一次拍摄操作未结束并返回 0。这是待处理操作状态；没有证据支持为了手动镜头而取消该检查。

公共 `doPhotoCapture` 在 `0x4014f984` 调用拍摄 API，随后忽略其返回值，并在 `0x4014f99c` 返回 1。因此，外层调用成功也不能替代请求、完成事件和成片证据。

C05 没有改写这两个检查，也没有启用上述生产标志。

## 尚未覆盖的再次就绪路径

同一主虚表 `+0x40 / +0x44 / +0x48` 分别指向 `0x406c18c4 / 0x406c1998 / 0x406c1a3c`。其中 `+0x48` 的函数读取原厂 App 的 `+0x458` 镜头脱离查询和 `+0x464` 故障查询，并会修改 `CORE+4` 的 `0x80000` 位及 `CORE+8` 的低位。S2 的入口恰好依赖这些状态。

当前没有证明调用它的完整事件链、各状态的实机时序或无镜头拍摄后再次就绪。不能直接取消其中的镜头检查或强制写入就绪位。C05 r2 的 S2 验证显式提供稳定取景状态，**不覆盖首次进入该状态或拍摄后的重复快门循环**。

接口复核还确认：原厂构造函数在对象 `+4` 绑定子接口虚表 `0x4076f990`，该表的 `+0x48` 是 `0x406ff364`（`bx lr`），并非主接口的 `0x406c1a3c`。曾筛出的 `0x40169d38` 则从全局 `0x409901ac` 取对象，而非相机全局 `0x4098f1cc`。这两类同槽号调用不能作为主接口方法已被调用的证据；按虚表槽号扫描不能证明重复拍摄事件链。
