## 新找到的缺口

C03／C04 将无镜头默认光圈表改为一档，但并非所有曝光程序线都使用该表。Smart Auto 的场景值 `0x12` 进入 `0x4024b38c` 的固定预设：复制参数，写入内部 `Av=96`、`Tv=-24`，然后调用 `0x4024aa18` 的 Manual AE 路径。该路径直接采用预设值，绕过此前的 AV 量化。

此次执行完整参数构造、所选程序线及 AE 输出更新后，观察到 C04 在这条无镜头路径仍输出 `[-24,96,91]`（Tv、Av、Sv 内部值）。因此，仅证明默认表为一档不足以证明全部相关程序线保持光圈不变。

场景值来自明确的模型输入，没有执行场景识别，也没有根据编号推测场景的物理名称。

## 新增修改

位置：代码段 1 偏移 `0x24aaf0`，分析地址 `0x4024aaf0`，长度 28 字节。完整前后字节在 `patches/manual-lens-c05.json`。

新代码在 Manual AE 输出已经形成后，检查主程序对象 `+0x6e` 的光圈节点数。只有节点数为 1 时，才调用原厂 `0x40249ed0`：把 Av 限制到唯一节点，并用 Tv 补偿保持 `Tv+Av`。

```text
ldrsh r0,[r8,#0x6e]
cmp   r0,#1
moveq r0,r8
moveq r1,r4
bleq  0x40249ed0
mov   r1,#0
strh  r1,[r4,#6]
```

替换区域原先调用 `0x4053d1e4` 计算一个未使用的 EV 值，并含一个后续不使用的比较。该计算函数只读取输入并返回数值，不写状态。新代码用一次半字写入保留原来的 `+6`、`+7` 两个输出字节清零；输出已有半字读写，地址保持原有对齐。没有移动函数、添加代码洞或修改其他代码段。

| 受控输入／路径 | C04 输出 Tv／Av／Sv | C05 输出 |
| --- | --- | --- |
| 无镜头默认单档表，Smart Auto 场景 `0x12` | `-24 / 96 / 91` | `8 / 64 / 91` |
| 默认单档表，M 的模型 AvSet=96、亮度=100 | `80 / 96 / 156` | `112 / 64 / 156` |

两组均保持 `Tv+Av` 和 Sv。内部值 64 仍是原厂默认模型量，**不是读取了手动镜头的实际光圈**。该特殊场景继续采用原厂固定曝光策略，此处只补偿其不可调光圈。

这项条件也覆盖原厂数据接口收到的单档光圈表，不能把它描述成仅检查“物理镜头脱离”。多档表跳过新补偿；原厂 9mm 的实际表和时序还没有抓取，仍需实机回归。单档电子镜头、极端光圈和曝光上下限也未完成实机验证。

## 原厂程序线执行验证

新增 `FlashAeProbe` 从原厂菜单行提交继续至闪光参数转换、`CAeInfoIF` 字段赋值、完整参数构造 `0x403160c8`、程序分发 `0x4043f3b4`、插值／AV 补偿及 `0x4053b364` 的 AE 输出更新。后者把软件闪光标志写到输出对象 `+0x28`，该字段由原厂诊断称为 `iFlashEnable`。

- 15 组模式／选项配置，分别用 3 个内部亮度输入执行程序线：原厂 Program、C05 Program、C05 自拍。自拍模式对应 AEMode 5；值 0 的软件闪光标志为 0，值 4／5／6／7 为 1。
- 4 组外闪状态字段对照，保留原厂 genuine／ready 等可用性规则；另有驱动值 3、HDR 值 2、镜头类别 0 的 3 组限制，均继续使 AE 软件闪光标志为 0。
- Smart Auto 的 6 个场景输入 `0,1,3,6,0x0d,0x12`，各比较 C04／C05 在 8 个亮度输入下的原始程序线。C05 无镜头默认表的 Av 全部保持 64；此前已受约束的路径不变，`0x12` 的固定预设得到上述补偿。普通场景中，模型亮度变化会改变 Tv／Sv；暗部和高亮极限仍可能受原厂策略限制。
- 两张合成多档镜头表，分别覆盖 P／A／S／M／自拍和 Smart Auto 固定场景，共 12 组模式／镜头表对照。C04／C05 的 Tv／Av／Sv、输出标志和软件闪光标志相同。**两张表均不是原厂 9mm 实测数据。**

这些执行使用原始整数除法、插值、参数构造及程序线代码，替代的依赖仍包括 RAM／初始设置、选中行、镜头表传输、内部亮度、场景编号、strobe 字段、场景参数、libc 内存操作、锁、时钟／日志和相机状态。标定刷新未加载，没有驱动 REALOS／ISP 或闪光硬件，也没有采集传感器测光。执行 `0x4053b364` 不等于完整 AE 任务及之后的硬件调度已经验证。

同时保留此前的 7 段独立解压、163 个资源和 writer 不变、已知校验、24 组 S2 路径、默认／收到镜头表／脱离回调、65,536 个模式菜单对照及设置 RAM 提交验证。记录位于 `research/generated/manual-lens-c05.json`。

首包完整回归 157 项通过；r2 更新后为 **159 项通过，0 失败、0 错误、0 跳过**。段 1 压缩长度为 5,301,894 字节，比官方增加 26 字节，仍在原分配空间内；其他段位置、writer、资源和整包长度不变。测试汇总为 `research/validation.json`。

## r2：启动阶段镜头通知的边界

r2 更新验证器和记录，固件二进制仍是上述 C05 哈希。执行原厂 `0x40267f60` 回调、应用虚表 `+0x18 → 0x403efadc` 的状态缓存，以及 `+0x1c → 0x403f06ec` 的延迟通知处理。

在启动等待标志为 0、输入回调事件 5 的模型中，原始指令写入：

| 字段 | 本次观察 |
| --- | --- |
| `CORE+0x28` | `0x10` 脱离位和 `0x04` 早期通知位被置位 |
| 应用对象 `+0x38` | 缓存位 `0x02` 被置位 |
| `CORE+0x24` | 产生早期／延迟处理标志；处理后对应两位清除 |
| 通知出口 | 延迟处理调用 `0x403ee4a4`，事件为 `(0x4d,5,0)` |
| `CORE+0` bit 0 | 回调及延迟处理均未将它设置为 1 |

后续 S2 对照显式使用镜头类别 0，并由模型提供已就绪／稳定取景条件。6 个模式均从原厂镜头拦截转至 C05 的拍摄分发；真实脱离位来自前述原指令回调，没有在这一步直接预置。另保留后期连接／ready 回调对照，以及底层模块状态 -1／-2／-3 的独立分类，避免把无镜头、未知模块和错误合并。

该结果只证明镜头通知和在给定就绪条件下的 S2 路径。队列出口采用模型，未执行消息投递、底层电气检测、模块状态到回调编号的转换、传感器就绪、中断或 REALOS 调度。`0x4050035c` 的启动完成函数会调用延迟处理，这是静态调用证据；完整启动过程没有执行。静态指令 `0x40258b1c` 的等待循环会检查 `CORE+0` bit 0，本次不能证明无镜头实机一定设置该标志或进入取景。

因此 `complete_cold_boot_emulated`、`no_contact_short_cold_boot_verified` 保持 false。应将实机无镜头开机是否出现实时取景、提示及快门行为纳入原厂基线。该段没有发现足以支持新增补丁的证据，未为了绕过未理解的启动等待而改写就绪位。

r2 工具包为 `dist/nxmini-evo-C05-offline-candidate-r2.zip`，固件镜像与首包一致。
