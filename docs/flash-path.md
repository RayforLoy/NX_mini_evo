# 自拍内闪路径：当前证据

最新 [C06 候选](candidate-C06.md)补齐外层 MENU、Fn 布局及 Fn 独立选项枚举。C05 仅改专用 `CMenuFlash` 内部列表，实测在原厂 9mm 下两个外层入口仍隐藏。C06 的入口、设置 RAM 和参数缓存通过受控 ARM 执行，屏幕显示和实际闪光待机身验证。

此前已在专用 `CMenuFlash` 找到自拍仅生成值 0 的菜单限制，修改进入 C04，并由 [C05 候选](candidate-C05.md)保留。C05 进一步执行原厂参数构造和自拍 AE 程序线，观察软件 `iFlashEnable`；实际充电、预闪、曝光同步和最终成片仍未验证。相机未参与这些离线测试。

2026-10-19 实机反馈：用户报告已刷入 C05、无镜头拍照有效；装着原厂 9mm 时，翻屏自拍中的闪光菜单入口仍被隐藏。该症状发生在 `CMenuFlash` 选项枚举之前，需优先定位外层菜单构造／模式过滤，不能继续把已解锁的内层选项作为完整修复。记录见 [实机反馈](../research/generated/c05-hardware-feedback-20261019.json)。

翻屏行为的边界：补丁针对 UI 模式 `0x2006`，不直接查询屏幕角度或修改翻屏输入。翻屏进入自拍模式后开放该模式的选项，仍由用户选择闪光；它不是“翻屏即强制闪光”。现有探针将自拍模式作为输入，没有执行真实翻屏到模式切换再到拍摄的整条链。镜头资格、驱动／HDR 等独立限制保留，因此不能把这一修改描述成所有镜头／转接环翻屏后都已能够闪光。

## 原厂 AE 程序线到软件闪光标志

C05 的 `FlashAeProbe` 从选中行提交继续执行 `0x40316cb4` 的闪光模式转换、`0x403160c8` 参数构造、`0x4043f3b4` 程序分发、普通自拍 AEMode 5 的 `0x4024ab3c`、通用闪光判断和插值，再执行 `0x4053b364` 的输出更新。菜单值 0 对应 AE 闪光模式 4，4／5 对应 1，6／7 对应 3；受控内闪字段下，后三组使软件 `iFlashEnable=1`。

执行还保留外闪 genuine／ready 等字段规则，以及驱动／HDR／镜头限制。镜头表、亮度、场景、strobe 字段和初始 RAM 等均有模型输入，没有测光、标定或闪光硬件。这里完成的是所选曝光程序线及该输出更新函数，不能据此排除其后完整 AE 任务或硬件调度中的限制。机器记录见 `research/generated/manual-lens-c05.json`。

## 新确认的菜单限制

闪光选择器是**十进制 10**；`0x40354a94` 对它有早期专用分支，先调用 `0x40354560`，并不继续执行后面的通用菜单构造。该分支构造 `0x403ff100` 的对象，其虚表 `0x4076a87c` 和 RTTI `10CMenuFlash` 已对应。

界面初始化 `0x403ff318` 调用 `0x403ff24c` 生成选项。原厂自拍 `0x2006` 落入默认分支，只有 `[0]`；Program、`0x200b`、`0x200c`、`0x200d` 为 `[0,4,5,6,7]`。这解释了先前的非零缓存写入模型为何不能排除实际界面限制。

C04 在 `0x403ff288` 修改一条指令，仅将自拍接入后一组选项，保留各项经过 `0x403ff11c` 的原厂可用性／元数据判断。原指令模式遍历对比覆盖 65,536 个 16 位编号，只有自拍列表改变；另执行逐项帮助函数并验证 3 个原厂限制仍拒绝。遍历中的帮助函数为记录器，逐项验证中的最终 UI 行接收、内存复制、EEPROM 输入、镜头类别、共享 UI 计数和日志采用显式模型，没有渲染或执行完整用户操作。

该结果和此前的缓存、AE 路径记录互补。机器证据见 `research/generated/manual-lens-c04.json`；C04 的 6 处修改包含 C03 的 5 处修改。下文保留此前分析边界及历史测试数。

## 原厂行存储与选中值提交

C04 r2 验证包继续执行 `0x403ff318` 初始化、`0x403fe49c` 的实际行结构写入和选中行提交。`0x403ff4b4` 从所选行 `+0xe8` 读取值，调用 `0x403ff434`；该函数经 CMenuLib 写设置并调用应用层闪光 setter，至原厂参数缓存边界。设置 byte getter／setter 均执行原指令，设置表描述符为 `0x4098f22c`，测试中的缓冲区和初值由模型分配。

15 组原厂 Program／C04 Program／C04 自拍对照显示，选中值能写入对应模式的 RAM 索引，且重新初始化界面后被读回。另验证选择原值时不写字节、不产生新的脏标记，以及 3 个原厂限制仍过滤菜单。C04 固件字节没有因此改变。

这个结果补上了原先“由模型直接给 setter 提供设置”的缺口，但仍以选中行作为输入，未执行真实按键／触摸、非易失存储、断电保持或物理闪光。完整依赖和停止位置见 C04 说明；不能将 RAM 写入称为 EEPROM 持久化成功。

## 已复核的绑定

启动代码 `0x40248ab4` 调用构造函数 `0x40267810`，随后通过字面量 `0x40248c78 → 0x4098f1cc` 保存对象。构造函数最终写入主虚表 `0x4076f5f0` 和 IQ 子对象虚表 `0x4076fb88`，两者 RTTI 都指向 `CCamSystemImpl`。

基类 `CCamSystem` 构造函数先写入另一组虚表，随后被派生类覆盖。只看基类会漏掉真实实现：IQ `+0xc8` 实际指向 `0x40695360`，该函数调整 `this` 后转至 `0x406c3ad0`。

| 位置 | 已确认的作用 |
| --- | --- |
| `0x40442af4` | 应用层读取有效闪光值，转换枚举并调用 IQ `+0xc8` |
| `0x40347fe8` | 有效值判断；驱动值 3、动态范围值 2、镜头资格不通过等条件会返回 0 |
| `0x40695360` | 派生类调整函数，将 IQ 子对象指针减去 `0x4f8` |
| `0x406c3ad0` | 实际闪光参数 setter；调用下列两个原始 RAM 写入函数 |
| `0x4040afd8` | 写共享 IQ 状态 `0x419f0538 + 0x11` 的一个字节 |
| `0x40345b48` | 写参数对象动态缓冲区的第 `0x1a` 个 u32，即偏移 `0x68` |

后两处是**参数缓存写入**。它们不是物理闪光触发，也不代表充电、预闪、曝光同步或最终闪光允许条件已经通过。

## 原指令执行结果

`FlashProbe` 使用原厂派生类虚表、调整函数、setter 及两段 RAM 写入指令；对象分配、EEPROM、镜头类别、状态查询和日志采用显式模型。每次使用新实例，并在缓存中预置非零哨兵，避免把未写入的初始 0 当成成功。执行在 `0x406c3b98` 停止，不执行后续硬件操作。

Program `0x2003` 使用 `EEP_FLASH 0x15f`，自拍 `0x2006` 使用 `EEP_FLASH_02 0x161`。在镜头类别模型为 1、普通驱动和非 HDR 输入下，两种模式对同一设置值产生相同缓存值：

| EEPROM 值 | IQ 字节 | 参数 `0x1a` |
| --- | --- | --- |
| 0 | 0 | 0 |
| 1／2 | 1 | 1 |
| 3 | 2 | 2 |
| 4 | 3 | 3 |
| 5 | 6 | 4 |
| 6 | 7 | 5 |
| 7 | 8 | 6 |

枚举的物理名称尚未全部验证，不将数值 4 直接命名为强制闪光。模型中服务上下文字节 `CORE+0x74` 分别取 0／6，共运行 32 组；该字节不是已经验证的 ISP 场景编号。

另外 3 组验证覆盖驱动值 3、动态范围值 2、镜头类别为 0。它们均使两处缓存清零，保留了原厂有效值限制。参数写入新增 19 项测试；后续 AE 模式转换再增加 7 项，目前完整回归 **139 项通过**。

这说明已追踪的原厂设置路径不会仅因为模式为自拍就无条件清零。它不能排除实机设置值不同、翻屏／美颜／倒计时组合、菜单输入限制、稍后覆盖缓存或更下层的禁闪条件。

## 自拍对应哪条 AE 路径

`AeModeProbe` 进一步执行应用层模式 setter `0x404410e4`、真实 IQ `+0x98` 调整函数 `0x40695040` 和相机场景 setter `0x406c2bdc`。随后执行原厂 `0x40316ea8` 的调用及写入序列，将 `0x4031390c` 返回值写到 `CAeInfoIF +0x80`，在 `0x40316eb4` 停止。相机参数对象仍由模型分配，其他未指定输入为 0；没有执行 AE 测光或求解。

| UI 模式 | 相机场景枚举 | GetCaptureMode | GetSmartProMode | 写入 AEMode |
| --- | --- | --- | --- | --- |
| Smart Auto `0x2002` | 9 | 0 | -1 | `0x15` |
| Program `0x2003` | 0 | 2 | -1 | 0 |
| 自拍 `0x2006` | `0x0c` | 1 | `0x23` | 5 |
| `0x200b` | 2 | 3 | -1 | 1 |
| `0x200c` | 3 | 4 | -1 | 2 |
| `0x200d` | 4 | 5 | -1 | 3 |

这些字段名由原厂诊断函数 `0x403174f0` 的字符串和读取偏移核对。表中的 Get3DMode 输入为 0；单独将它设为 1 的对照会使自拍返回 AEMode `0x1c`。因此，不能把 `0x1c` 程序线中的禁闪直接认定为普通自拍限制，更不能删除 Get3DMode 判断来宣称修复自拍。

静态追踪显示，`0x4043f3b4` 对 AEMode 5 调用 `0x4024ab3c`，该程序线包含通用闪光判断 `0x40249f34`。原厂诊断 `iFlashEnable` 则通过选择器 `0x2c`，沿 `0x40342494 → 0x40336e90 → 0x40314fd8 → 0x403137d8`，读取 `0x4053b014` 返回对象的有符号半字 `+0x28`。`0x4053b364` 会把程序线输出的 `+9` 字节写入此字段。这部分是静态证据，未在本次探针中执行整个运行时路径。

排查时另核对了 `0x40344160`：原厂诊断将其结果写入 **AdaptiveToneOn**，不能把它当成闪光可用性判断。普通自拍 GUI 也会调用与 Program 相同的闪光绘制槽 `+0x6c → 0x403284a8`；画面绘制不等于按钮可操作或物理闪光允许。

## 复现

先按项目 README 安装环境并提取官方 1.10；以下使用本工作区现有的提取目录：

```powershell
.\.venv\Scripts\python.exe tools/probe_flash.py --decoded work/nxmini-1.10-verified/decoded/chunk-01.bin
.\.venv\Scripts\python.exe -m pytest -q tests/test_probe.py
```

记录保存在 `research/generated/flash-parameter-probes.json`，包含原件哈希、虚表绑定、每组模型输入、依赖调用、停止位置和缓存结果。

下一步需要将自拍进入时的真实设置、拍摄准备和下层 AE／闪光状态查询连接起来；美颜服务、倒计时和翻屏状态分别保留为待验证因素。最新 C04 已修改上文的菜单分支，实际拍摄与恢复仍待验证。
